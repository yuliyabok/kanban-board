# Как устроен проект простыми словами

Схемы к этому объяснению лежат в `docs/architecture_diagrams.md`.

Этот проект постепенно превращается из одного Flutter-приложения в систему из
двух частей:

- приложение, которое открывает пользователь;
- сервер, который будет хранить общие данные, авторизацию и синхронизацию.

Сейчас приложение уже умеет много работать локально. Это значит: данные лежат
на устройстве в локальной базе Drift, интерфейс быстро открывается, а будущий
сервер подключается отдельным слоем, не ломая экран задач.

## Главная идея

Представь проект как кафе.

- Flutter-приложение — это зал, где сидит пользователь: доски, карточки,
  календарь, Гант, комментарии, история.
- Локальная база Drift — это блокнот официанта: все быстро записывается рядом,
  даже если интернет пропал.
- Сервер — это большая кухня и склад: там общая правда для всех пользователей.
- `kanban_contracts` — это меню и правила заказа: приложение и сервер одинаково
  понимают, как называется маршрут, какие поля есть у ошибки, события,
  истории задачи и синхронизации.

## Что происходит, когда пользователь меняет задачу

1. Пользователь нажимает кнопку или меняет поле в карточке.
2. UI вызывает use case или command service.
3. Repository записывает изменение в локальную Drift БД.
4. Карточка на экране обновляется сразу, потому что UI слушает локальную БД.
5. Если включен серверный режим, remote datasource пытается отправить изменение
   на сервер.
6. Если сервер недоступен, запись остается локально как pending через
   `syncAction`.
7. Позже `SyncManager` сможет отправить pending-изменения и подтянуть свежий
   `/sync/delta` с сервера.

Поэтому приложение остается отзывчивым: пользователь не ждет сеть на каждое
движение карточки.

## Что такое local/server режим

В `AppConfig` есть `RemoteMode`:

- `local` — приложение работает само на себе, remote-слой имитируется локальными
  datasource. Это удобно для разработки UI.
- `server` — приложение использует HTTP/WebSocket datasource и ходит в Dart
  backend.

По умолчанию стоит `local`, чтобы текущая разработка не ломалась из-за того,
что сервер еще scaffold.

## Где лежат основные части

### Корень проекта

- `README.md` — краткое описание проекта и команды запуска.
- `Makefile` — удобные команды `make get`, `make analyze`, `make test`,
  `make server-run`.
- `docker-compose.yml` — локальный PostgreSQL для будущей серверной базы.

### Flutter-приложение

Flutter-приложение физически живет в `apps/kanban_app`:

- `apps/kanban_app/pubspec.yaml` — зависимости Flutter-приложения.
- `apps/kanban_app/lib/main.dart` — вход в приложение.
- `apps/kanban_app/lib/src/app` — роутинг, тема, запуск приложения.
- `apps/kanban_app/lib/src/core` — общая инфраструктура: база, сеть, sync,
  провайдеры.
- `apps/kanban_app/lib/src/features` — фичи: задачи, доски, комментарии,
  пользователи,
  календарь, Гант и так далее.

### Shared contracts

`packages/kanban_contracts` — общий пакет для приложения и сервера.

Он не знает про Flutter, Drift или UI. Его задача — описать общий язык:

- API routes;
- формат ошибки;
- realtime event;
- sync delta;
- историю задачи;
- summary “Что изменилось, пока вас не было”.

Если маршрут или DTO используется и клиентом, и сервером, лучше класть его сюда.

### Dart-сервер

`apps/kanban_server` — серверная часть.

Сейчас это уже не просто пустой scaffold:

- `/health` уже отвечает, что сервер жив;
- auth endpoints уже умеют регистрацию, логин, refresh/logout и `/auth/me`;
- auth хранит пользователей и refresh sessions в PostgreSQL;
- users/workspaces endpoints уже умеют поиск текущего пользователя, создание
  workspace, список workspace и список участников;
- boards/columns/task types endpoints уже умеют базовый CRUD;
- tasks/comments/assignees/history endpoints уже умеют базовый CRUD и пишут
  историю изменений с `actorUserId`;
- `/changes/summary` возвращает DTO правильной формы;
- `/sync/delta` возвращает пустую delta правильной формы;
- остальные доменные endpoints пока возвращают `501 not_implemented`;
- `/realtime` пока работает как WebSocket echo-заготовка.

Это нормально: цель текущего шага — подготовить границы, а не написать весь
backend сразу.

## Для чего нужны главные core-файлы

- `app_config.dart` — хранит адрес API, WebSocket, имя локальной БД и режим
  `local/server`.
- `api_client.dart` — общий HTTP-клиент на Dio. Через него API datasource ходят
  на сервер.
- `api_endpoints.dart` — локальный фасад над shared routes. Нужен, чтобы старый
  код мог использовать `ApiEndpoints`, а настоящие пути жили в contracts.
- `core_providers.dart` — центральная сборка зависимостей: база, конфиг,
  API-клиент, realtime, sync.
- `sync_manager.dart` — координатор синхронизации. Сейчас уже умеет различать
  local/server режим и получать `/sync/delta` в server-режиме.
- `realtime_connection.dart` — низкий уровень WebSocket-соединения.
- `realtime_service.dart` — более удобный слой realtime events для фич.

## Как запустить

Установить зависимости везде:

```bash
make get
```

Проверить код:

```bash
make analyze
```

Запустить тесты:

```bash
make test
```

Запустить сервер:

```bash
make server-run
```

Поднять PostgreSQL:

```bash
docker compose up postgres
```

## Что будет следующим логичным шагом

1. Добавить серверный list endpoint для columns и подключить его к pull.
2. Расширить `SyncManager`: отправка pending-записей и применение server delta.
3. Сделать realtime не echo-заготовкой, а настоящей рассылкой событий.
4. Реализовать invitations/users beyond search, когда server endpoints готовы.
5. Довести persistent outbox, tombstones и conflict resolution.

Главное правило: UI не должен знать, локально работает приложение или через
сервер. UI говорит с repository, repository говорит с local/remote datasource,
а режим выбирается через provider/config.
